How a customer reaches the screen

The browser does not talk directly to PostgreSQL. Each layer has a focused responsibility and calls the next layer.

  1. Next.js receives the page request. The file is apps/web/app/customers/page.tsx.
  2. Authentication derives the current user. Development currently falls back to demo-user.
  3. The domain function scopes the query. It follows User → Employee → Business and returns only that business’s customers.
  4. Prisma translates the typed query to SQL. The client connects to the local PostgreSQL server.
  5. React renders the results. Loading, empty, and error files cover the asynchronous states.

Ownership model introduced by the prototype

Software platform └── Business (tenant/security boundary) ├── Location: Downtown ├── Location: North Side ├── Employee → User: demo-user └── Customers ├── Aisha Brown ├── Maria Lopez └── James Wilson
Security rule: do not trust a business ID sent by a browser. Start with the authenticated user and derive the allowed business on the server.

Dependency direction

Apps may import packages, but one app must not import another app. Shared logic belongs in a package. The @project scope is a repository placeholder and should not be hardcoded into newly invented package names.

Files you should not edit manually

  • .pgdata/ — PostgreSQL’s local data files.
  • .azurite/ — local Azure emulator data.
  • packages/db/src/generated/ — regenerated by Prisma.
  • Applied migration files such as 0001_init.sql — migrations are append-only.
  • .env files unless you intentionally manage local secrets; never commit them.
Database layers

Schema, migration, client, and data are different things

1. Prisma schema

schema.prisma describes the desired models and relations used by TypeScript.

2. SQL migration

A numbered .sql file changes an existing PostgreSQL database to match the new design.

3. Generated client

pnpm prisma:generate creates typed query code from the Prisma schema.

4. Seed data

pnpm db:seed creates predictable local records for development and demonstrations.

Correct database-change sequence

  1. Agree on the behavior and relationships.
  2. Edit packages/db/prisma/schema.prisma.
  3. Generate a new append-only migration; never rewrite an applied one.
  4. Review generated SQL before applying it. Tools may propose destructive statements.
  5. Apply the migration and confirm the migration tracker records it.
  6. Run pnpm prisma:generate.
  7. Update repeatable seed data.
  8. Add tests that prove ownership boundaries.

How to start the current project demo

Use the focused two-terminal startup for a presentation. It avoids extra worker/Azurite noise and prevents accidental duplicate database servers.

Preparation — repository terminal

cd "C:\Users\Juanc\OneDrive\Desktop\Webdevelopment Fall\Fall Project\Clientflow_CRM-"
git switch learning/company-customers
pnpm install
pnpm prisma:generate

Normally pnpm install is only needed after a fresh clone or dependency change.

Terminal 1 — database

pnpm db:dev

Wait for:

postgres ready — this process owns the data

Terminal 2 — seed

pnpm db:seed

Expected:

seeded demo business, locations, employee, and customers

Terminal 2 — web app

pnpm dev:web

Open these URLs

URLWhat to show
http://localhost:3000/api/health{"status":"ok","db":"ok"} proves the web process can reach PostgreSQL
http://localhost:3000/customersThe company-scoped customer list from the seed data

Stop cleanly

  1. Press Ctrl+C in the web terminal.
  2. Press Ctrl+C in the database terminal.
  3. Wait for PostgreSQL’s shutdown message before closing the window.
Avoid duplicate servers: do not run pnpm dev, pnpm db:dev, or pnpm dev:web twice. A second database process will fail on port 5433, and a second web process may move to port 3001.

Feature implementation ritual

  1. Issue: describe why, behavior sketch, out-of-scope items, and verification sketch.
  2. Spec: write observable behavior, examples, failures, constraints, and verification.
  3. Implementation: derive identity, validate, scope the query, act, map errors, and revalidate.
  4. Tests: include happy path plus a failure that would catch removal of the feature.
  5. Review: read the diff, run the complete checks, and verify the documented drill.

Database safety rules

  • Every query is scoped from the current user.
  • Foreign or unknown resources return 404, not 403.
  • Never edit an applied migration; add the next numbered migration.
  • Writes that imply history must save the record and history event transactionally.
  • Do not edit or commit .pgdata, .azurite, or .env.
  • Review generated SQL before applying it.
